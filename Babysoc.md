# VSDBabySoC – RTL to Gate-Level Verification

## objective

VSDBabySoC is a small SoC design that brings together a RISC-V based digital processing block and analog interface components. The main digital processing is handled by the **rvmyth** processor, while the **avsdpll** and **avsddac** blocks provide clock-generation and DAC functionality.

The objective of this work is to understand the transition of the design from RTL to a synthesized gate-level implementation and to verify that the synthesized circuit continues to behave as expected.

The complete flow followed in this project is:

**RTL Setup → RTL Simulation → Logic Synthesis → Netlist Analysis → Gate-Level Simulation → Waveform Comparison**

---

# 1. Project Setup

A dedicated directory was created for working with the BabySoC design. The required project repository was then cloned into this directory.

```bash
mkdir baby_soc
cd baby_soc/
git clone https://github.com/Subhasis-Sahu/BabySoC_Simulation
cd BabySoC_Simulation
```

The repository contains the required modules, libraries, include files, and simulation environment needed for the experiment.

---

# 2. Understanding the Design

The `vsdbabysoc` module acts as the top-level module of the SoC.

The design consists of three important functional sections:

- **rvmyth** – RISC-V based processor core responsible for digital processing.
- **avsdpll** – Generates the required clock signal for the digital section.
- **avsddac** – Receives digital data from the processor and produces the corresponding DAC output.

The processor output is available through the `RV_TO_DAC[9:0]` bus. This signal is useful during simulation because it allows the digital data generated by the processor to be monitored.

The testbench supplies the clock and reset conditions required to start the SoC and observes the resulting output signals.

---

# 3. RTL Simulation

RTL simulation was performed before synthesis so that the behavior of the original design could be established.

The RTL was compiled using Icarus Verilog with the `PRE_SYNTH_SIM` definition:

```bash
iverilog -o ./pre_synth_sim.out -DPRE_SYNTH_SIM src/module/testbench.v -I src/include/ -I src/module/
```

The simulation executable was then started:

```bash
./pre_synth_sim.out
```

The simulation generates a VCD file containing the signal transitions. This waveform data can be viewed using GTKWave:

```bash
gtkwave pre_synth_sim.vcd
```

### Signals Monitored

During RTL simulation, the following signals were examined:

- `CLK`
- `reset`
- `RV_TO_DAC[9:0]`
- `OUT`

The RTL simulation is treated as the baseline for checking the behavior of the synthesized implementation later in the flow.

# 4. RTL Synthesis Using Yosys

After checking the RTL simulation, synthesis was performed using **Yosys**.

The required RTL modules were read into the synthesis environment:

```bash
read_verilog src/module/vsdbabysoc.v
read_verilog -I src/include/ src/module/rvmyth.v
read_verilog -I src/include/ src/module/clk_gate.v
```

The library descriptions required for synthesis and technology mapping were loaded:

```bash
read_liberty -lib src/lib/avsdpll.lib
read_liberty -lib src/lib/avsddac.lib
read_liberty -lib src/lib/sky130_fd_sc_hd__tt_025C_1v80.lib
```

The top-level design was specified and synthesized:

```bash
synth -top vsdbabysoc
```

The sequential elements were mapped to the flip-flop cells available in the SKY130 library:

```bash
dfflibmap -liberty src/lib/sky130_fd_sc_hd__tt_025C_1v80.lib
```

Logic optimization and cell mapping were then performed:

```bash
opt

abc -liberty src/lib/sky130_fd_sc_hd__tt_025C_1v80.lib
```

The synthesized design was cleaned and normalized using:

```bash
setundef -zero
clean -purge
rename -enumerate
```

Finally, the synthesis statistics were generated and the gate-level Verilog description was written to a file:

```bash
stat

write_verilog -noattr baby_soc_net.v
```

### Purpose of Synthesis

Synthesis converts the behavioral RTL description into a structural representation made from hardware cells. During technology mapping, generic logic is replaced with cells from the selected SKY130 standard-cell library.

The generated `baby_soc_net.v` therefore represents the hardware implementation obtained after synthesis rather than the original behavioral RTL.

# 5. Analysis of the Synthesized Netlist

The synthesized Verilog netlist was examined to understand the hardware generated from the RTL.

At the functional level, the major blocks of the SoC can still be identified. The processor receives its clock from the PLL section and produces digital information on the `RV_TO_DAC` interface. This digital information is connected to the DAC block.

After technology mapping, the digital logic inside the processor and supporting logic is represented using standard cells from the SKY130 library.

Therefore, the synthesized design contains many instances of logic gates, flip-flops, buffers, and other standard cells connected together.

### Difference from RTL

The RTL describes **what the circuit should do**, while the synthesized netlist describes **how the circuit is implemented using library cells**.

As a result, the synthesized netlist is considerably more detailed than the original RTL.

---

# 6. Gate-Level Simulation

The synthesized netlist was subsequently used for Gate-Level Simulation (GLS).

Unlike RTL simulation, GLS uses the synthesized gate-level representation along with the standard-cell Verilog models. This makes it possible to check whether the logic produced by synthesis behaves consistently with the original RTL.

The post-synthesis simulation was compiled using the following command:

```bash
iverilog -DPOST_SYNTH_SIM -DFUNCTIONAL \
-I src/include/ \
-I ../../sky130RTLDesignAndSynthesisWorkshop/my_lib/verilog_model/ \
-I src/module/ \
src/module/testbench.v
```

The generated executable was run using:

```bash
./a.out
```

The post-synthesis waveform was viewed using:

```bash
gtkwave post_synth_sim.vcd
```

### Objective of GLS

The main purpose of GLS is to validate the synthesized representation against the expected RTL behavior.

The simulation checks whether the signals generated by the gate-level circuit follow the same functional sequence observed during RTL simulation.

8. The GLS waveform followed the functional behavior observed at RTL.

---

# Conclusion

This project provided practical understanding of how a System-on-Chip design moves from an RTL description toward a technology-mapped gate-level implementation.

The RTL was first used as the functional reference, followed by synthesis using Yosys and mapping to the SKY130 standard-cell library. The generated netlist was then simulated at gate level and compared against the original RTL simulation.

The matching functional behavior between the two simulation stages demonstrates that the synthesized design correctly represents the intended RTL functionality.

Overall, the experiment gives hands-on exposure to important ASIC design steps such as RTL verification, synthesis, technology mapping, netlist inspection, and Gate-Level Simulation.
